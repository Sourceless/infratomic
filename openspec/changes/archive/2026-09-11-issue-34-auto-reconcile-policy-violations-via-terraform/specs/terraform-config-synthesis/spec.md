## Purpose

Lets a previously-unmanaged resource (or a specific offending child resource) be brought under Terraform's control just long enough to be destroyed, by having the AWS provider generate its configuration from live state rather than this codebase serializing HCL itself.

## ADDED Requirements

### Requirement: Config synthesis uses Terraform's native import block and generated config
Synthesizing configuration for a previously-unmanaged resource SHALL be done using Terraform's native `import` block together with `terraform plan -generate-config-out` and `terraform apply` — letting the resource's provider generate the resource's configuration body from live state via the provider schema. No attribute-map-to-HCL serialization (generic or per-resource-type) SHALL be authored by this codebase; the only HCL authored directly is the minimal `import { to = ..., id = ... }` block.

#### Scenario: A resource's configuration is generated by the provider, not hand-serialized
- **WHEN** synthesized import+destroy remediation runs for an unmanaged resource
- **THEN** the resource's Terraform configuration is produced by `terraform plan -generate-config-out` from the resource's own `import` block, not by this codebase mapping the resource's attributes to HCL text itself

### Requirement: The import block's target address reuses the resource's existing identifier
The `import` block's `to` address SHALL reuse the target resource's existing `:resource/id` value verbatim (already shaped as `<resource_type>.<local_name>`, matching what Terraform's `to =` expects), without synthesizing a separate local name for the import.

#### Scenario: A Discovered Resource's stored id becomes the import block's target address
- **WHEN** an import block is generated for a Discovered Resource being remediated
- **THEN** the block's `to` address is exactly that resource's stored `:resource/id` value

### Requirement: The import id is derived per resource type's id-space
The `import` block's `id` value SHALL be derived as follows:
- For a resource type whose stored AWS id is itself a valid Terraform import id (e.g. `aws_security_group`, using its stored `id` attribute, `sg-xxxx`): that stored id is used directly.
- For a resource type whose AWS id-space does not match Terraform's expected import-id shape (e.g. `aws_security_group_rule`, `aws_route`): Terraform's synthetic composite import id SHALL be built from the resource's own already-stored attributes (for `aws_security_group_rule`: `<security_group_id>_<type>_<protocol>_<from_port>_<to_port>_<source>`), rather than using the stored AWS id directly.

#### Scenario: A security group is imported by its stored AWS id
- **WHEN** an import block is generated for a Discovered `aws_security_group`
- **THEN** the block's `id` value is that security group's stored `id` attribute, used directly

#### Scenario: A security group rule is imported by a synthesized composite id
- **WHEN** an import block is generated for an offending `aws_security_group_rule`
- **THEN** the block's `id` value is the composite id built from that rule's own stored attributes (security group id, type, protocol, port range, source), not its stored AWS-assigned rule id

### Requirement: Synthesis and destroy run in an isolated, per-invocation scratch working directory
Every synthesized import+destroy remediation SHALL run in a dedicated scratch working directory, distinct from the shared working directory `terraform apply` reconciliation uses, with its own minimal provider/backend configuration. This working directory SHALL be created fresh for that invocation and discarded unconditionally once the import+destroy sequence completes, whether it succeeded or failed. This applies uniformly to every synthesized-import remediation, including remediation of a New-Child-Drift child resource.

#### Scenario: A synthesized import does not affect the shared working directory
- **WHEN** synthesized import+destroy remediation runs for an unmanaged resource
- **THEN** no configuration is written into the shared working directory that `terraform apply` reconciliation uses, and that directory's own state is unaffected by the synthesis

#### Scenario: The scratch working directory is discarded after a failed synthesis
- **WHEN** a synthesized import+destroy sequence fails partway through (e.g. `terraform plan -generate-config-out` or the subsequent apply/destroy errors)
- **THEN** the scratch working directory created for that invocation is still discarded, and no dangling synthesized configuration remains for a later reconciliation pass to pick up

### Requirement: The synthesized resource is destroyed after being imported
Once a resource has been imported into the scratch working directory via the generated configuration, reconciliation SHALL destroy that resource (`terraform destroy`) within the same scratch working directory before that directory is discarded.

#### Scenario: An imported resource is destroyed in the same working directory it was imported into
- **WHEN** synthesized import+destroy remediation completes its import step for an unmanaged resource
- **THEN** that same resource is destroyed within the same scratch working directory, prior to the directory being discarded
