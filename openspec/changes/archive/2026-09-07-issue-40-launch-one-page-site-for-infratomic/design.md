## Context

See `proposal.md` for motivation. Binding constraints from the issue's alignment decisions (this design implements them, not re-derives them):

- Single landing page only — no multi-page docs site, no blog, no "how it works"/architecture section, no `sourceless.org` link.
- Features list is split into "Available now" (Policy Checks, Reachability graph search) and "On the roadmap" (blast-radius simulation, safe-deploy-ordering solver, Reachability auto-fix), each roadmap item its own line item.
- "Available now" copy uses `CONTEXT.md`'s canonical glossary terms; roadmap copy uses the talk's own language since no canonical terms exist for those yet — `CONTEXT.md` itself is not touched.
- Quickstart reuses README's real CLI commands (the policy-gated `apply` example) nearly verbatim — must remain copy-pasteable and actually work against the real CLI.
- This PR commits the `CNAME` file and the Pages workflow, but does not perform or depend on the DNS repoint or GitHub Pages enablement — those are manual, out of this PR's tasks.
- No Node/Hugo/static-site build tooling exists anywhere in this repo (`flake.nix`'s dev shell is `git`/`nix`/`jdk17`/`clojure` only) and none is being added.

## Goals / Non-Goals

**Goals:**
- Ship one static HTML page, styled with plain CSS, with zero build step and zero new dev-shell/tooling dependency.
- Deploy it via GitHub Actions + GitHub Pages using only the workflow's built-in `GITHUB_TOKEN` (no external secrets), following this repo's existing minimal-secrets CI convention.
- Make the page's factual claims about features consistent with what's actually implemented (per `openspec/specs/policy-check` and `openspec/specs/network-topology`/`iam-reachability`) and with `CONTEXT.md`'s glossary, so the site doesn't overclaim relative to the codebase.
- Leave the repo in a state where enabling Pages and repointing DNS (both manual, both out of scope here) are the *only* remaining steps to satisfy the issue's "site is live" acceptance criterion.

**Non-Goals:**
- Any JS framework, static site generator, CSS framework/build pipeline, or new language runtime added to this repo's toolchain.
- A "how it works"/architecture section, a blog, or additional pages — explicitly excluded by the issue and the alignment decision.
- Performing the DNS repoint or enabling GitHub Pages in repo settings — both require access (registrar, repo admin) this change doesn't have and doesn't attempt to substitute for.
- Design assets (logo, diagrams, screenshots) — none exist in the repo today and none are added; the page is text/CSS only.

## Decisions

### Page location and structure: `site/index.html` + `site/style.css`, deployed as the Pages artifact root

A new top-level `site/` directory holds exactly two files: `index.html` (the page markup) and `style.css` (all styling, linked via a relative `<link>`). Keeping the site's source in its own top-level directory (rather than, say, `docs/`) avoids any collision with `docs/user-guide.md`/`docs/adr/*`, which are contributor-facing and not part of the published page, and keeps "what gets uploaded to Pages" an unambiguous single directory (`site/`) rather than a filtered subset of `docs/`.

`CNAME` is committed inside `site/` (not the repo root) so it uploads alongside `index.html` as part of the same Pages artifact — GitHub Pages requires `CNAME` to live at the root of the *published* content, which is `site/`, not the repo root, given the workflow uploads only that directory.

**Alternative considered**: put the page at the repo root (`index.html` at top level) so it could theoretically also be served by GitHub's legacy branch-based Pages mode. Rejected — this repo already uses Actions-based Pages deployment (`actions/deploy-pages`) for the one CI convention it has, and a root-level `index.html` would sit awkwardly next to `README.md`, `deps.edn`, `flake.nix`, etc. with no clear boundary of "what's the site."

### Content sourcing: hand-authored copy, not templated from README/CONTEXT.md/the talk script

The page's HTML is hand-authored once, using README's quickstart commands and CONTEXT.md's glossary terms as source material to copy from — not generated by a script that reads those files at build/deploy time. There is no build step in this repo's toolchain to run such a script, and a hand-authored page is trivially fast to review for the accuracy/terminology concerns the alignment decision raised (canonical terms for shipped features, no overclaiming on roadmap items).

**Alternative considered**: a small script (Clojure, since that's this repo's only language) that extracts the CLI quickstart block from `README.md` at deploy time, so the two never drift. Rejected as unnecessary machinery for a single quickstart block on a single page under a tight deadline — if the CLI's example commands change, updating both README and the site page by hand is a two-line diff, not a maintenance burden that justifies build tooling this repo doesn't otherwise have.

### Deployment workflow: new `.github/workflows/pages.yml`, modeled on `state-backend-image.yml`'s structure

A new workflow, triggered on `push` to `main` (paths-filtered to `site/**` and the workflow file itself, so unrelated app-code pushes don't redeploy the site) and on `workflow_dispatch` (manual redeploy), with:

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

— the two `pages`/`id-token` permissions are new to this repo (the existing workflow only needs `contents: read` / `packages: write`), required by `actions/deploy-pages`' OIDC-based deployment. Steps: `actions/checkout`, `actions/upload-pages-artifact` with `path: site`, `actions/deploy-pages`. No `test` job is needed the way `state-backend-image.yml` has one — there's no code to test, only static files to upload; the closest equivalent is `actions/upload-pages-artifact`'s own success/failure as the validation that a well-formed artifact was produced.

The workflow does not attempt to enable Pages itself (`gh api repos/.../pages`) — that's a one-time, repo-admin, out-of-band action per the alignment decision. If Pages isn't yet enabled with `build_type: workflow`, this workflow's `deploy-pages` step will simply fail until that manual step happens; this is expected and documented in `tasks.md`, not treated as a defect in the workflow itself.

**Alternative considered**: trigger on every push to `main` regardless of path. Rejected — would redeploy the (unchanged) site on every unrelated Clojure-code commit, adding noise to the Pages deployment history for no benefit.

### No "how it works" section, no sourceless.org link — enforced by page structure, not just by omission

The page has exactly two `<section>`s (quickstart, features) plus a minimal header (tagline/hook) and footer (license link to `LICENSE`, GitHub repo link). There is no third section reserved or commented-out for a future architecture write-up — if that's wanted later, it's a new change against this same `site` capability, not a currently-dormant part of this one.

## Risks / Trade-offs

- **The site can be fully correct and merged, yet the issue's literal acceptance criterion ("site is live and reachable at `https://infratomic.org`") still won't be true** until the manual DNS/Pages steps happen → Accepted per the alignment decision; `tasks.md` calls this out explicitly as a follow-up outside this change's own task list, and the issue stays open until verified.
- **Hand-authored quickstart copy can silently drift from the real CLI commands in `README.md`** if either is edited later without updating the other → Accepted trade-off documented above (no build-time extraction); mitigated by keeping the quickstart block short (one command sequence) so a manual diff-check is cheap.
- **A path-filtered workflow trigger (`site/**`) means a future contributor could add a workflow-triggering change elsewhere in `.github/workflows/pages.yml` itself without realizing the filter needs updating if `site/`'s location ever changes** → Low risk given `site/`'s location is fixed by this design; called out here rather than treated as a hidden gotcha.

## Migration Plan

- Purely additive: no existing file's content changes (README, CONTEXT.md, LICENSE, existing workflow, existing specs are all read-only inputs, not edited).
- No rollback complexity — reverting this change removes `site/`, `CNAME`, and the new workflow file, and Pages (once enabled) would simply have nothing new to deploy on the next run of a reverted workflow, or `main` would need force-manual `deploy-pages` re-run to un-publish, at the discretion of whoever operates Pages.
