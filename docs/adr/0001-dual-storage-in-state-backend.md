# Dual storage of raw state and decomposed resource entities in the state backend

Terraform's `http` backend contract requires `GET` to return the exact raw state JSON last `POST`ed, byte-for-byte — but the issue also requires one queryable Datomic entity per resource (type, name, attributes, version reference), which is impossible to serve with fidelity if state is reconstructed from decomposed entities. We chose to write both representations on every `POST`, in a single transaction: an opaque raw-JSON string on a `state-version` entity (served verbatim for `GET`), and upserted `resource` entities (keyed by `(type, name)` via a unique identity attribute) derived from that same payload for querying. This trades some storage duplication and a small chance of the two views drifting apart (they're written atomically in one tx, so this is only a risk if the derivation logic itself has a bug) for never needing to reconstruct Terraform's own on-disk state format — a format we don't control and don't want to become responsible for round-tripping perfectly.

Considered and rejected: decomposing state into entities only and reconstructing the raw JSON for `GET` on demand — rejected because Terraform's state schema is intricate (backend-specific metadata, ordering, fields we don't model) and any reconstruction risks Terraform rejecting or misreading state on a subsequent `plan`/`apply`.
